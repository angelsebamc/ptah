# Code smells

The smells the Standards reviewer looks for in changed code, from Martin Fowler's *Refactoring*, chapter 3.

Report a smell only where the change introduces it or makes it worse. The fix column is what to write on the finding's `Fix:` line, made concrete for the code at hand.

| Smell | What it looks like | Fix |
|---|---|---|
| **Mysterious Name** | A function, variable, or type whose name doesn't say what it does or holds | Rename it to say what it does or holds |
| **Duplicated Code** | The same logic in more than one place, including code that copies an existing helper, code that looks different but does the same job, and the same lines in every branch of a conditional | Extract the shared logic into one function, or call the existing one; pull it up into the superclass when the copies are in sibling subclasses, keeping only the steps that differ in each; extract it into a class both use when the copies are in unrelated classes; keep the better algorithm when two do the same job; move lines repeated in every branch out of the conditional |
| **Long Function** | A function that does several things, or has a block that needs a comment to say what it does | Extract each such block into a function whose name says what the comment would have said |
| **Long Parameter List** | A function that takes more than three or four parameters, often because some of them choose which algorithm runs | Let the function get a value it can compute or query itself, pass the whole object instead of several values taken from it, group the rest into one parameter object, and split a function that takes a flag into one function per case |
| **Feature Envy** | A function that uses another module's data more than its own | Move the function, or the part that envies, to the module that owns the data |
| **Data Clumps** | The same group of values passed or stored together in several places, such as a database's connection settings; if one value is removed, the others no longer make sense | Introduce one type or object for the group, pass the whole object instead of its separate values, and move the code that works on the group into it |
| **Primitive Obsession** | Strings, numbers, or booleans standing in for a domain concept (money, a status, an id) | Replace the primitive with a small type for the concept |
| **Repeated Switches** | The same `switch` or `if` chain on the same value in more than one place | Replace the switches with one lookup or polymorphism |
| **Shotgun Surgery** | One logical change that needs small edits across many files | Move the scattered pieces into one module, or a new one when none fits, and inline any class the move leaves nearly empty |
| **Divergent Change** | One module that changes for several unrelated reasons, such as one class whose finding, displaying, and ordering methods all change when a product type is added | Split the module so each part changes for one reason |
| **Lazy Element** | A class or function that does too little to be worth its own name, often shrunk by refactoring | Inline it into its caller; collapse a subclass that adds almost nothing into its superclass |
| **Speculative Generality** | Parameters, hooks, abstractions, or options nothing uses yet | Remove the unused generality |
| **Temporary Field** | A field set only for one algorithm or case and empty the rest of the time, often added to avoid passing parameters | Move the field and the code that uses it into its own class, and replace the checks for whether it is set with a null object |
| **Message Chains** | Long chains of calls to reach an object (`a.b().c().d()`) | Hide the chain behind one method on the first object |
| **Middle Man** | A class or function that only delegates to another | Remove it and call the delegate directly |
| **Insider Trading** | A class that reaches into another class's private fields and methods, or two classes that depend on each other's internals | Move the fields and methods to the class that uses them; move what both need into a new class and hide it behind a method; make a two-way reference one-way; when a subclass is too tied to its superclass's internals, replace the inheritance with composition |
| **Large Class** | A class that keeps growing new features because adding to it is easier than making a new class, and now has several unrelated jobs | Split out each job into its own class |
| **Alternative Classes with Different Interfaces** | Two classes that do the same job under different method names, often because the author of one didn't know the other existed | Rename and reshape the methods until the classes share one interface, then delete one class; when only part of the job is shared, move that part into a superclass both inherit from |
| **Data Class** | A class with only fields and getters and setters, while the logic that works on its data lives in the classes that use it; a plain record or data transfer object meant only to carry data is fine | Move the logic from its callers into the class, hide its public fields and collections behind methods, and remove setters nothing should call |
| **Refused Bequest** | A subclass that uses only some of what it inherits, and leaves the rest unused or overrides it to throw | When the classes have nothing real in common, replace the inheritance with composition; when they do, move only what the subclass needs into a new superclass that both inherit from |
| **Comments** | A comment that explains what the code does because the code doesn't say it itself; a comment on why is fine | Split a commented expression into variables named for its parts, extract a commented block into a function named after the comment, rename a function whose comment explains it, and turn a comment stating a required condition into an assertion |
